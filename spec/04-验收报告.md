## C. API 错误路径

21 条用例。

- **方法白名单**：POST/PUT/DELETE/PATCH/HEAD/OPTIONS/小写 `get` 全部 400 `CTX_BAD_REQUEST`，且不触碰引擎（无副作用）✅
- **路由形状**：`/`、`''`、`/session`、`/session/s1`、`/session/s1/context/extra`、`/session/s1/`、`/session//context`、`/ctx/api/session/s1/context`（重复前缀）、`/foo/bar/baz` 全部 400 `unknown route` ✅
- **会话不存在**：context / output-text / file 三端点一致 404 `CTX_SESSION_NOT_FOUND` ✅；会话不存在 + index 越界时会话错误优先（先 `loadAggregate` 后校验 index）✅
- **index 解析**：`3/99/-1/-0.5/1.5/abc/NaN/Infinity/1e2/0x10/null` → 400 `CTX_INDEX_OUT_OF_RANGE`；缺参/空串 → 400 `CTX_BAD_REQUEST` ✅
- **异常收敛**（关键）：`TypeError/ReferenceError/RangeError/SyntaxError` 从 `readSession` 或 `traceSession` 抛出 → **500 `CTX_INTERNAL`**，message 脱敏为 `internal error`（不含路径）✅；普通 `Error`（数据层故障）→ 归一为 404，且内部信息不外泄 ✅
- **子会话失败隔离**：子会话读取抛错 → 主会话照常 200，该子徽标 `degraded=true` ✅
- **六错误码 → HTTP 状态码映射表**逐条实测：404/404/403/400/400/500 与 §3.6 完全一致 ✅
- **registerCtxApi HTTP 粘合层**（既有 spec 未覆盖）：注册形状 `kind='prefix'`、`path='/ctx/api'`；前缀剥离正确；`content-type: application/json; charset=utf-8` 与 `cache-control: no-store` 齐全；查询串不干扰路由；`req.url` 缺失时按 `/` 处理并返回 400（不挂起连接）；`req.method` 缺省按 GET 处理 ✅

## 发现并修复的问题清单

### 源码侧（我方最小修复，共 3 处，请 team-lead 判断是否转派工程师复核）

**#1 · 高风险 · `src/host/aggregator.ts:582`（原 `segments.sort(...)`，现改为 582-592）**

- **问题**：`segments` 排序时，`outputFullTexts`（与其下标一一对应的未截断全文侧信道）**没有同步排序**。合并顺序是「主会话全部段 → 子会话全部段」，而最终展示顺序是按时间重排。只要子会话的输出在时间上落在主会话两条输出之间（子 Agent 在会话中途被派发，**这是最常见的多 Agent 形态**），二者就错位，`output-text?index=N` 会返回**另一段**的全文。
- **复现**：主 t=1000 `MAIN-FIRST`、主 t=3000 `MAIN-SECOND`、子 t=2000 `CHILD-MIDDLE` → 修复前 `GET output-text?index=1` 返回 `MAIN-SECOND`（应为 `CHILD-MIDDLE`）。
- **改动**：先构造 `{segment, full}` 配对数组，排序后再拆回两个数组，保证下标严格对齐。

**#2 · 中风险 · `src/host/aggregator.ts:615`（原 `injectEntries.set(path, {})`，现改为 615-623）**

- **问题**：注入文件树的条目不带 `agents`（`TreeEntry` 只写了 `{}`），而 `agents` 是 §3.3 明确的三棵树**共用**字段。client 的 `filterTree`（`src/client/panes/InputPane.tsx:24`）按 `node.agents` 过滤，导致**一旦选中某个 Agent，注入文件树必然整棵清空**，与「按 Agent 筛选」需求相悖。
- **改动**：按 `pluginItems` 的 `agentKey` 归集到 `injectEntries[path].agents`（去重，主在前）。

**#3 · 低-中风险 · `src/host/aggregator.ts:649-652` + `src/shared/types.ts:64`**

- **问题**：`outputsTruncated` 只反映「输出段数量超 500」，不反映「单条输出正文超 4KB 被截断」。而 `inputsTruncated` 是「条目数超限**或**单条文本超限」双口径。结果：输出段被静默截断时，client 顶部不出现任何「已截断」提示，违背 §7.4「所有截断/降级都置位 PayloadBudgets」。
- **改动**：`outputsTruncated` 增加 `|| segments.some(s => s.textTruncated)`；同步更新 `types.ts` 的字段注释。
- 缓解因素：client 在单卡上有 `line-clamp` 视觉压缩和「查看全文」入口，故非静默数据丢失。
