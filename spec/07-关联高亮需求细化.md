## 1. 需求口径（用户澄清，已定稿）

### 1.1 主线是因果，不是同源

原始需求为「点击输入、参考、输出中的任何一个，高亮有关联的输入、参考和输出」。经澄清，此处「关联」指**因果链**，用户的三种表述如下：

| 点击 | 期望看到 | 用户原话 |
|---|---|---|
| 参考 | 哪些输入最终引导到读这个文件；读了之后有哪些输出 | 「点了一个参考，我就知道哪些输入最终会参考到这个文件，参考了之后有哪些输出」 |
| 输出 | 哪些输入影响到这个输出；这个过程中有哪些参考 | 「点某一个输出，就看哪些输入有影响到这个输出，这个过程中有哪些参考」 |
| 输入 | 这个输入整条线：输出是什么、参考是什么 | 「点输入，就是这个输入整一条线，输出是什么、参考是什么」 |

**同源关联降级**：用户指出「高亮同源的情况是比较少的，顶多一个文件在输入里有、输出里有、参考里也有」。故同源不作为独立一期，待因果链路完成后顺带实现——判据仅为路径相等，成本近乎为零。

### 1.2 中间过程不算

用户明确：界面展示的是「每一轮的输入和最终的输出，中间过程都不算」。

这条约束有两个直接后果：

1. **关联粒度落到轮次级**，而非「相邻两条输出段之间」的步隔级；
2. **过程输出段默认不参与关联**——它默认不显示。仅当用户打开「显示过程输出」开关（v1.1 已有该开关）后，可见的过程段才纳入关联计算。**可见性是参与关联的前提**。

### 1.3 关联的方向性

因果是有方向的，高亮须遵循时间方向：

- 点**输入** → 只关联它**之后**的参考，之前的查阅与这一问无关；
- 点**参考** → 只关联它**之前**的输入，其后才出现的输入不构成原因；
- 点**输出** → 关联它所属轮次的输入与参考，二者在时间上都先于这条结论。

反直觉但正确的情形：同一栏里的两条输入，点较早的那条时，较晚的那条不亮；点某个参考时，时间上晚于它的输入不亮。

## 2. 关联模型

### 2.1 两类锚点

| 类别 | 锚点 | 归属 | 命中点数量 |
|---|---|---|---|
| **单线锚点** | 用户输入条目、系统注入条目、输出文字段 | 恒属单一 Agent | 1 个 |
| **汇聚锚点** | 参考文件节点、输出文件节点、注入文件节点 | 可被多个 Agent 操作 | N 个（每个涉及的 Agent 至少一个） |

文件是多个 Agent 的交汇点。用户举例：「点了一个输出物 C，Agent A 也改了它、Agent B 也改了它，那么 Agent A 改它的这一轮和 Agent B 改它的这一轮，也都得高亮起来。」

### 2.2 轮次的切分

**轮次不依赖 `turn` 字段，由输入栏自己切分，且由 host 在聚合末期统一计算并下发**（见 §3.5）。

对某个 Agent X，取输入栏中归属 X 的**有效用户输入条目**（`inputs.userItems` 中 `agentKey === X` 且 `inputKind !== 'inherited'` 者，按 `time` 升序）记为 `I₁, I₂, …, Iₙ`：

- 第 k 轮区间 = `[Iₖ.time, Iₖ₊₁.time)`，k < n
- 第 n 轮区间 = `[Iₙ.time, +∞)`
- 若 n = 0（该 Agent 无有效用户输入条目），整条时间轴视为第 1 轮

**定位规则**：给定时间戳 t，其所属轮次为满足 `Iₖ.time ≤ t` 的最大 k。**时间戳并列时以 `seq` 兜底比较**——子会话重放父上下文时可能成批写入同一毫秒，仅比 `time` 会让并列条目区间退化为零长，进而把后续操作全部归到最后一条。

**分轮标尺排除两类条目**：

- **`pluginItems`（系统注入）**：AGENTS.md、skill 文档等不构成「用户的一问」，不能用来分轮；但它落在某轮区间内时，作为该轮的输入参与高亮。
- **`inherited`（继承上下文）**：子会话 `descriptor` 之前重放的父历史（`aggregator.ts:595` 判定）。它并非该子 Agent 真实收到的一问，若计入标尺，子 Agent 有 N 条 inherited 就被切出 N 个伪轮，真实委派轮被推到末尾。**inherited 只作落轮成员（落在某轮区间内时参与高亮），不参与切分。**

> **为什么不用 `turn`**：`turn` 是会话内编号，主会话与每个子会话各有 `turn = 1`，跨 Agent 不可比，用它做关联键会产生大量虚假关联。以输入条目为标尺则天然跨 Agent 可比（靠 `time`），且省去一轮字段补齐。

### 2.3 统一算法

```
输入：锚点 A
输出：高亮集合

① 求命中点集 H = {(agentKey, round)}
     A 为单线锚点  →  H = {(A.agentKey, A.round)}
                       （输入条目 round 由 host 下发（§3.5）；输出段沿用既有
                        turn→round 机制但须换算为本模型轮次，见 §3.5 说明）
     A 为汇聚锚点  →  H = 该文件节点上 host 预计算的全部 (agent, round) 对
                       （FileOpStamp 已按 (agent, 轮次) 去重，见 §3.2）

② 对每个 (agentKey, k) ∈ H，展开三栏：
     输入栏 → round === k 且 agentKey 相同的输入条目（用户输入、注入、inherited 均按
              host 标注的 round 匹配）
     参考栏 → refStamps 中存在 (agent, round=k) 的文件节点
     输出栏 → round === k 的**可见**输出段
              （可见性受「显示过程输出」开关控制，见 §2.3.1）

③ 各命中点展开结果取并集
④ 结果与「筛选后可见集合」取交集（见 §4.2，防高亮到被 Agent 筛选剔除的节点）
```

> **H 是集合，不是映射**：同一 Agent 可在不同轮次重复命中。同一文件被同一 Agent 在多轮操作时，H 中会出现该 Agent 的多个轮次，各轮独立展开后并入结果（见 §2.6）。
>
> **轮次由 host 预计算，client 只做相等匹配**：轮次边界依赖输入条目定序，而输入条目在合并排序（`aggregator.ts:1094`）之后才稳定——此时 host 顺手为每个输入条目、每次文件操作、每个输出段标注轮次号，client 端关联计算退化为 `(agentKey, round)` 相等比较，不再跑时间区间定位。这同时落实 v1.1 的既有分层原则「所有聚合逻辑在 host 完成，client 只做展示与筛选」。

#### 2.3.1 输出栏不做特例

输出段与其他两栏适用**同一条轮次区间规则，无例外**——尤其是**不为最终答复开后门**。

最终答复在时间上位于该 Agent 时间线末端，只落在最后一轮区间内。若点第 1 轮的输入却高亮第 5 轮的结论，就与本模型反复强调的方向性自相矛盾——那条结论并非这一问的结果。

因此**默认状态下，点非最后一轮的锚点时输出栏为空**。这是「中间过程不算」的真实反映，不是缺陷：那一轮确实没有可见输出。

**两项配套**：

1. **空态提示**：输出栏未命中任何可见输出段时，显示一行说明（「本轮无可见输出 · 开启过程输出可补全链条」），避免用户误判为功能失效。
2. **开关的新意义**：「显示过程输出」由此从「查看历史」变为**因果链的补全开关**——开启后各轮过程段可见，点早期输入时输出栏才有内容可亮。默认关闭是刻意权衡（避免撑爆视口），但用户一旦需要完整因果链，它就是入口。

> **注**：这与 §8 第 2 项「点输出时的收紧口径」是两件事。此处讨论的是**非输出锚点**是否连带高亮最终答复（结论：不连带）；第 2 项讨论的是**点最终答复时**回溯范围是否放宽到全部轮次。

### 2.4 完整关联表

| 点击锚点 | 输入栏高亮 | 参考栏高亮 | 输出栏高亮 |
|---|---|---|---|
| **用户输入条目** I（Agent X 第 k 轮） | I 本身（锚点）+ 同轮注入条目 | X 在第 k 轮区间内读取的文件 | 第 k 轮区间内的可见输出段（**默认常为空**） |
| **系统注入条目** J（Agent X 第 k 轮） | J 本身（锚点）+ 同轮用户输入 | X 在第 k 轮区间内读取的文件 | 第 k 轮区间内的可见输出段（同上） |
| **参考文件** R（被 X₁…Xₙ 读过） | 各 Xᵢ 在各自读取轮次的输入条目 | R 本身（锚点）+ 同路径的其他栏节点 | 各 Xᵢ 读取轮次区间内的可见输出段 |
| **输出文字段** O（Agent X，第 k 轮） | X 在第 k 轮的输入条目 + 同轮注入 | X 在第 k 轮区间内读取的文件 | O 本身（锚点） |
| **输出文件** C（被 X₁…Xₙ 改过） | 各 Xᵢ 在各自写入轮次的输入条目 | C 本身（锚点）+ 同路径参考节点 | C 本身（锚点）+ 各 Xᵢ 写入轮次区间内的可见输出段 |

### 2.5 多 Agent 汇聚示例

沿用用户所举场景：输出物 C 被 Agent A（第 2 轮）与 Agent B（第 1 轮）分别改过。

| Agent | 时间线 | 点 C 的结果 |
|---|---|---|
| A | 提问1 → 读 config → **提问2 → 读 pool → 改 C** | 亮提问2、读 pool；**不亮**提问1 与读 config（属第 1 轮） |
| B | **委派指令 → 读 schema → 改 C** → 读 test → 最终答复 | 亮委派指令、读 schema；**不亮**读 test 与最终答复（发生在改 C 之后） |

两条时间线各自按自己的轮次回溯，互不相干，最后取并集——不是按全局时间切一刀。B 改完 C 之后仍读了 test、仍说了结论，但那些不构成「改 C」的原因。

**输出栏的处理**：两轮区间内均无可见过程段（默认隐藏），故输出栏只亮锚点 C 本身；A 与 B 的最终答复都不亮——它们不在改 C 所在的轮次内。

### 2.6 同一 Agent 多轮命中与范围退化

**同一 Agent 也可命中多个轮次**。用户所举场景：Agent A 在第 1 轮「提问1 → 读 Config → 改 C」，第 2 轮「提问2 → 读 Config → 改 C」。此时 H = `{(A,1), (A,2)}`，两轮各自展开后并入，结果为：提问1、Config、提问2 全部亮起。**最终答复不亮**——它属于第 2 轮之后，不在任何命中轮次区间内（§2.3.1）。

> Config 在两轮各被读一次，但参考栏仅一个节点，高亮一次即可，**不重复计数**——高亮是布尔态，不是计数器。

**由此暴露的问题**：文件被操作的轮次越多，高亮范围越大；贯穿全程的文件会退化成全选，高亮随之失去筛选意义。这与 §8 第 2 项「点输出时的收紧口径」是同一类问题。

| 应对 | 做法 | 取舍 |
|---|---|---|
| **甲（推荐）** | 栏头显示「命中 N 轮」 | 最轻，保住信息完整；用户看到「命中 2 轮」即明白范围为何如此大 |
| 乙 | 默认只聚焦最近一轮，可展开全部 | 更聚焦，但多一次交互，且默认隐藏早期轮次 |

**推荐甲**。乙会隐藏早期轮次，而用户在上述场景中明确期望「提问一、Config、提问二都亮」——隐藏提问一与诉求相悖。

## 3. 数据需求

### 3.1 现状

| 实体 | 时序与归属 | 是否够用 |
|---|---|---|
| 用户输入 / 系统注入条目 | `seq` `time` `agentKey` 完备 | 够用 |
| 输出文字段 | `seq` `time` `turn` `step` `agentKey` 完备 | 够用 |
| 参考文件节点 | 仅 `viewCount` 与 `agents[]`，**无逐次读取的时序与归属** | **缺口** |
| 输出文件节点 | 仅 `outputOp` 与 `agents[]`，**无逐次写入的时序与归属** | **缺口** |

`aggregator.ts:126` 的 `RefView { count, agents }` 与 `:131` 的 `OutputOp { op, agents }` 都只保留结果态。而链路是通的：`:451-454` 的 `tool/call` 分支已读到事件时间，`:478-490` 的 `tool/result` 经 `callId` 回配原调用。

### 3.2 补齐方案（经代码审查修订）

```ts
/** 一次文件操作（读取 / 写入）的归属与轮次。host 预计算，client 只做相等匹配。 */
export interface FileOpStamp {
  /**
   * 操作所属 Agent，取**该文件节点 `agents` 子数组**的下标（非全局 agents 数组，
   * 见下方审查裁定 ②），client 一次映射还原。
   */
  agentIndex: number
  /** 操作所属轮次（该 Agent 自己的轮次序号，host 按 §2.2 规则预计算）。 */
  round: number
}
```

`FileTreeNode` 增加两个可选字段，沿用现有「按用途挂可选字段」惯例（与 `viewCount` / `outputOp` 同构）：

```ts
/** 参考树专用：逐次读取的 (Agent, 轮次)，已按 (agentIndex, round) 去重。 */
refStamps?: FileOpStamp[]
/** 输出树专用：逐次写入的 (Agent, 轮次)，同上。 */
outputStamps?: FileOpStamp[]
```

**代码审查裁定（三点，均已核实）**：

- **① 时刻取 `tool/result` 侧，不取 `tool/call` 侧**。`classifyToolResult`（`aggregator.ts:490`）本就拿不到 call 时刻；且参考的成立以 result 为准——未配对调用不计数（`:483`）、isError 不计参考（`:487`），都是既有口径。故在 `:490` 调用点直接传 `event.time`，**不改动 `ToolCallRecord`，也不必裁定「call 还是 result」**（answer：result）。
- **② `agentIndex` 存文件节点自身 `agents` 子数组下标，不存全局 agents 下标**。全局 `agents` 数组在 `:1142-1197` 才定型，而扫描与 refs/outputs 合并（`:1010-1091`）都早于它——采集期取不到全局下标，强行存会错位。改为：扫描期 stamps 存 `agentKey`，树构建期对每文件的 agents 子表做一次 `agentKey → 子表下标` 重映射。单文件涉及 Agent 通常 1~3 个，压缩收益相同且无顺序耦合。
- **③ 注入树不补 stamps**。`injectEntries`（`:1116-1128`）建树时丢弃了 time/agentKey，看似缺口；但 `PluginInjectItem` 的 `time` / `agentKey` / `filePaths` 都完整下发，client 侧按 `filePaths.includes(path)` 反查即可得到 (Agent, 时刻) 列表，**host 零改动**。注入文件节点的汇聚锚点数据由 client 自行推导。

host 侧合计约 60 行（原估 40 行 + 审查发现的签名贯通、轮次计算、重映射）。

### 3.4 载荷与降级（经审查修订）

审查发现原估算两处失真：JSON 对象单条约 35B 而非 8B；且 `MAX_REFERENCE_FILES = 2000` 个文件各至少 1 条 stamp 就吃掉全局 4000 预算的一半，「同文件多轮命中」的核心场景反而没有余量。**根因是按操作次数去重——而关联判据只需要「落在哪一轮」**。

**修订：stamps 按 `(agentIndex, round)` 去重，同轮只留一条**。同一 Agent 同一轮内读一个文件 10 次，与读 1 次，对关联结果毫无差别（高亮是布尔态）。去重后单文件的 stamp 数 = 涉及的 (Agent, 轮次) 组合数，16 条预算即可覆盖 16 个轮次组合，与 §2.6 的核心场景自洽。

| 项 | 取值 |
|---|---|
| 单锚点体积 | 约 30 B（JSON 对象两个数字字段） |
| 单文件上限 | 16 个 (Agent, 轮次) 组合 |
| 全局上限 | 4 000 条，最坏约 120 KB；典型会话数 KB |
| 淘汰方向 | 超出保留**最新**的轮次组合（与输出段淘汰方向一致） |

**超限不置 `budgets` 标记**——关联精度下降不等于「数据未计入」，不宜与既有截断横幅混同语义。

> **已知降级**：单文件涉及的 (Agent, 轮次) 组合超 16 个时保留最新，该文件**早期轮次**的关联丢失。按 (agent, round) 去重后，触发条件从「操作 16 次」放宽到「跨 16 个轮次组合」，真实会话中已属极端。
>
> **输入与输出淘汰方向错位（审查发现）**：输入条目超限**保留最早**（`aggregator.ts:371` / `:409` 直接 break），输出段保留**最新**。超长会话会出现「输入停在中段、输出只剩末尾」，末轮区间 `[Iₙ.time, +∞)` 吞掉全部剩余操作，高亮退化成全选。**缓解**：`budgets.inputsTruncated === true` 时，关联结果附带降级标记，栏头提示「输入条目超限，轮次划分可能失真」，不静默。

### 3.5 轮次的计算与命名冲突

轮次计算插入在 `aggregator.ts:1094`（合并排序完成）之后：

1. 对每个 Agent，取其 `userItems` 中 `inputKind !== 'inherited'` 的条目按 time 升序作为标尺，算出轮次边界；
2. 为该 Agent 的**全部**输入条目（含 injected 与 inherited）标注落轮 `round`；
3. 对 refs / outputs 的 stamps 按 `time` 定位轮次（并列时 `seq` 兜底，§2.2）；
4. 输出段：**废弃复用既有 `OutputTextSegment.round`**——它由 `turn` 首现序重编号（`aggregator.ts:1097-1106`），与本模型的「输入条目切分轮次」同名不同义，跨会话合并后两者可能出现错位（如子会话的 turn 与主会话交错）。输出段改用新标注的 `causalRound`，既有 `round` 字段保留不动（过程输出折叠分组仍在用，勿动）。

> **命名约定（审查发现）**：既有 `round` = turn 首现编号（`types.ts:244`），本模型的轮次一律叫 `causalRound`，两个概念不得混用。

## 4. 关联计算的位置

新增 `src/client/relations.ts`，产出锚点 → 高亮集合的纯函数：

```ts
/** 关联锚点（判别联合，覆盖单线与汇聚两类）。 */
export type RelationAnchor =
  | { kind: 'input'; id: string }        // userItems / pluginItems 条目
  | { kind: 'output-text'; id: string }  // textSegments 段
  | { kind: 'file'; path: string; tree: 'reference' | 'output' | 'inject' }

/** 高亮集合：三栏各自的命中 id / path。 */
export interface RelationResult {
  inputIds: ReadonlySet<string>
  outputIds: ReadonlySet<string>
  /** 命中的 (agentKey, 轮次)，供栏头计数与提示文案使用。 */
  hitPoints: readonly { agentKey: string; causalRound: number }[]
  /** 文件命中分档：strong = 该文件的 stamp 恰好落在命中轮次；weak = 仅同路径沾边（M2 同源用）。 */
  filePaths: { strong: ReadonlySet<string>; weak: ReadonlySet<string> }
  /** 输入条目超限导致的降级标记（§3.4），栏头提示用。 */
  degradedByInputTruncation: boolean
}

export function computeRelations(
  aggregate: ContextAggregate,
  anchor: RelationAnchor,
  selectedAgentKey: string | null,
  options: { showProcess: boolean },
): RelationResult
```

- 纯函数、无 React 依赖，可脱离 DOM 单测，与既有 `selectors.ts` 同构；
- **接收 `selectedAgentKey` 并把结果与「筛选后可见集合」取交集**（审查发现）：`filterTree`（`InputPane.tsx:24-36`）按 Agent 剔除节点，选中 A 时仅被 B 操作的文件根本不在视图里，若不取交集会高亮不存在的节点、栏头计数（`RefPane.tsx:28-43`）也对不上。交集即「关联结果 ∩ 可见结果」，筛选与联动同时成立；
- 轮次已由 host 预计算（§3.5），client 只做 `(agentKey, causalRound)` 相等匹配，无时间区间扫描；
- 注入树锚点由 client 从 `pluginItems.filePaths` 反查（§3.2 裁定 ③）；
- **目录节点作为锚点**：取其子树全部文件 stamps 的并集，运行时计算、不落库（审查发现：目录行在 `FileTree.tsx` 可点击，stamps 却只挂叶子）；
- `options.showProcess` 决定过程段是否参与——**可见性即参与条件**。

## 5. 交互方案（待定）

### 5.1 冲突：点击已被抽屉占用

三栏内点击条目与文件节点一律打开抽屉查看正文。若将单击改为触发关联，正文查看路径即被挤占。

### 5.2 四个候选

| 方案 | 触发方式 | 抽屉 | 评价 |
|---|---|---|---|
| A | 单击 = 关联，双击 = 抽屉 | 双击 | 语义最简，但改变既有肌肉记忆，且双击在树节点上易误触 |
| **B（推荐）** | 条目 hover 浮现「链路」按钮，点击设锚点；本体点击仍开抽屉 | 单击不变 | 两条路径互不挤占，可发现性由 hover 与图例承担 |
| C | 悬停即高亮，无需点击 | 单击不变 | 最轻，但高亮随指针漂移、无法驻留比对 |
| D | 单击同时触发关联与抽屉 | 单击 | 抽屉遮住高亮结果，等于白高亮 |

**推荐 B + 悬停轻提示**：hover 未点击时关联项以淡色预示，使关联范围可「扫一眼」获得；点击链路按钮则锁定锚点，保持至再次点击、按 `Esc`、或点击栏内空白处。

### 5.3 呈现

- **三档强度**：锚点（强边框 + 实底）／强关联（主色淡底 + 左侧色条）／弱关联（淡底无侧条）。**单一强调色**，不引入多色，避免与 Agent 徽标、类型标签争视觉。
- **非关联项保持原样**，不做整体降透明度——三栏长列表中降透明会碍于扫读。
- **计数与定位**：栏头追加「关联 N」；高亮项若不在视口内须 `scrollIntoView`，否则高亮不可见等于无效。定位仅在首次设锚点时做一次，落点取首个强关联项，弱关联不触发滚动。
- **命中轮次提示**：锚点为汇聚锚点且命中多轮时，栏头追加「命中 N 轮」（§2.6 应对甲），使高亮范围偏大这件事对用户可解释。
- **空态提示**：某栏未命中任何条目时，栏内显示一行说明而非留白。输出栏文案须点明补救路径（「本轮无可见输出 · 开启过程输出可补全链条」），**不得**显示成"无关联"——关联是有的，只是该轮没有可见输出。

### 9.1 历次修订中被推翻的判断

|---|---|---|
